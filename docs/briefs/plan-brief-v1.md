# Plan 지침 v1 — 초등 영어 단어 "손으로 잡기" 게임

작성: 2026-11-26, 코디네이터
대상: Plan 서브에이전트 (Opus 5.5, 추론 강도 높음)

## 1. 너의 일

이 게임을 **어떻게 만들지** 계획을 세워 `spec.md` 한 파일로 저장한다. 구현은 하지 않는다.
spec.md는 뒤이어 일할 Build·Review 서브에이전트가 따르는 **유일한 설계 기준**이 된다. 그들이 이 문서만 읽고 같은 결과를 낼 수 있을 만큼 구체적으로 쓴다.

## 2. 수정 범위 (엄수)

- **만들 수 있는 파일: `/Users/sungchul/Desktop/play2/영어게임/spec.md` 하나뿐.**
- 다른 파일을 만들거나 고치지 않는다. `npm install`, `git init`, 코드 파일 작성 금지.
- 조사를 위한 읽기(파일 읽기, 웹 문서 확인, `npm view` 같은 조회)는 자유.
- 형제 폴더(`/Users/sungchul/Desktop/play2/selectio game`, `.../game2`)는 이 사용자가 예전에 만든 게임이다. spec.md 쓰는 방식·기술 스택의 참고용으로만 **읽는다**. 고치지 않는다.

## 3. 프로젝트 요구 (사용자 원문 요약)

- 초등학교 영어 교육과정 수준의 영어 단어 퀴즈 문제 **100개 이상**.
- 화면 위에서 영어 단어 **3~4개가 흩어져 아래로 떨어진다**.
- 화면에 **영어로 된 설명**(뜻풀이/힌트)이 나오고, 그에 맞는 단어를 잡으면 점수가 오른다.
- **태블릿 카메라**로 사용자의 손을 인식한다. 사용자가 실제로 손을 단어 위치에 해당하는 허공으로 옮겨 **손을 움켜쥐면(주먹)** 단어를 잡은 것으로 본다.

## 4. spec.md에 반드시 담을 것

1. **기술 선택과 이유**
   - 손 인식 방법(예: MediaPipe Tasks Vision의 Hand Landmarker 또는 Gesture Recognizer 등). 브라우저에서 돌아가는지, 모델·wasm 파일을 어디서 받는지(CDN vs 저장소에 포함), 버전 고정. **공식 문서를 직접 확인**하고 확인한 날짜와 주소를 적는다.
   - 앱 형태(정적 웹앱 권장 — 카메라는 HTTPS 또는 localhost에서만 열림). 빌드 도구·언어(형제 프로젝트는 Vite + TypeScript를 썼다 — 맞추는 쪽을 기본으로 검토).
   - 배포: GitHub에 푸시하고 GitHub Pages로 여는 것을 기본안으로 검토(태블릿에서 HTTPS 주소로 열 수 있어야 함). 상대 경로 문제 등 주의점.
2. **화면 좌표 대응**: 카메라 영상 좌표 → 게임 화면 좌표 변환, 거울 모드(좌우 반전), 화면비가 다를 때 처리.
3. **"움켜쥐기" 판정 규칙**: 손가락 랜드마크로 주먹을 판정하는 구체적 계산식(임계값 포함), 떨림 방지(여러 프레임 연속 확인, 히스테리시스), 잡는 순간의 손 위치를 어느 점으로 볼지, 단어 판정 영역(여유 반경). 펼침→쥠 "전환"에서만 잡기가 일어나게 하는지 등.
4. **게임 규칙**: 한 라운드 흐름, 떨어지는 단어 수(3~4)·속도·배치(겹치지 않게 흩어지기), 정답/오답/놓침 처리, 점수·목숨·시간, 난이도 상승, 시작/일시정지/결과 화면. 초등학생이 서서 팔을 움직이는 상황(태블릿과의 거리, 피로, 한 판 길이)을 고려한다.
5. **문제 데이터 설계**: 100개 이상 문항의 형식(예: `word`, `clue`(쉬운 영어 설명), 학년군, 주제, 한국어 뜻, 오답 후보를 고르는 방법). 근거로 삼을 어휘 기준(교육부 고시 초등 영어 권장 어휘 등)을 밝힌다. **문항 100개 이상의 실제 목록을 spec.md에 넣을지, Build가 만들고 Review가 검증할지** 정하고, 어느 쪽이든 품질 기준(설명이 정답 하나만 가리키는지, 설명에 정답 단어가 들어가지 않는지, 설명 문장이 초등 수준인지)을 적는다.
6. **카메라가 없거나 거부됐을 때**: 마우스/터치로도 할 수 있는 대체 입력(개발·검증에도 필요), 오류 안내 문구.
7. **개인정보**: 영상은 기기 밖으로 보내지 않음, 저장하지 않음. 화면에 안내.
8. **성능 목표**: 태블릿(iPad Safari, 안드로이드 Chrome)에서의 프레임 목표, 인식 해상도, 인식을 매 프레임 돌릴지 등.
9. **파일 구조**: 폴더·파일 목록과 각 파일의 책임.
10. **검증 방법**(Review가 실제 손 없이 확인하는 법): 판정 로직 단위 테스트(랜드마크 좌표를 직접 넣어 주먹/펼침 판정), 문항 데이터 검사 스크립트, 브라우저 자동 테스트(예: Playwright + 가짜 카메라 또는 녹화한 랜드마크 재생, 디버그 입력 모드) 등. 무엇을 자동으로 확인하고 무엇은 사람이 태블릿에서 직접 확인해야 하는지 나눈다.
11. **Build 작업 순서**: 단계별로 나누고 각 단계의 완료 기준.
12. **사용자 확인 필요** 절: 사용자가 정해야 할 갈림길마다 선택지와 **추천안**을 적는다(예: 대상 학년, 한국어 뜻 표시 여부, 소리·발음(TTS), 한 판 시간/목숨 방식, GitHub 저장소 이름·공개 여부, 배포 방식). 추천안만으로도 바로 만들 수 있게 쓴다.
